# EXP-001 — Effect of Store Buffer Size on Append Performance

## Status
**Status:** Pilot completed; protocol not yet locked; final measurements not started.

## 1. Research question
How does the Store buffer size affect append throughput and latency in Logos under a controlled append-only workload?

## 2. Motivation and scope
Logos uses a `bufio.Writer` in `internal/core/store.go` to buffer framed records before writing them to the underlying file. This experiment studies the effect of configuring that writer's buffer size on the Store append path.

This is a characterization of the current Logos implementation under a specified workload and environment. It does not establish a universally optimal buffer size, filesystem-independent behavior, durability guarantees, or superiority over other storage systems.

## 3. Implementation under test
- Repository: `github.com/ccrabbai/logos`
- Component: `internal/core.Store`
- Benchmark: `BenchmarkStoreAppend`
- Benchmark source: `internal/core/store_benchmark_test.go`
- Configurable constructor: `NewStore` 
- Buffer size `0`: preserves the existing `bufio.NewWriter` default behavior.
- Explicit values: use the configured `bufio.Writer` buffer size.

Record the exact Git commit and working-tree state in `environment.md` before final runs.

## 4. Variables and measurements

### Independent variable
Store writer buffer size, in bytes.

### Dependent variables

Primary:
- append throughput (`MB/s`)

Secondary:
- average append time (`ns/op`)
- allocations per operation (`allocs/op`)
- allocated bytes per operation (`B/op`)

Correctness:
- successful append and read-back verification for every tested buffer configuration.

### Latency measurement boundary

This experiment does not report median, p95, or p99 append latency.

The Go benchmark reports aggregate `ns/op`, which represents average elapsed time per benchmark operation for each run. Per-operation latency instrumentation was not added because the Store append path is sufficiently short that instrumentation overhead could alter the workload being measured.

If latency distributions become a research question later, they should be investigated as a separate experiment with a measurement method designed specifically for that purpose.

### Controlled variables
Keep constant across configurations:
- record payload size and contents;
- number of append operations per benchmark iteration;
- benchmark implementation and Go version;
- machine, operating system, storage device and filesystem;
- repository revision and build environment;
- concurrency (the initial benchmark is single-threaded);
- benchmark command and timing options.

The benchmark creates a fresh temporary file for each sub-benchmark. Document any further changes to the harness before final measurements.

## 5. Workload
The current pilot uses a fixed 1,024-byte payload and calls `Store.Append` repeatedly in a single goroutine. The Store frames each payload with an 8-byte length header. The reported throughput uses `b.SetBytes(1024)`, so it describes payload bytes per second rather than total framed bytes per second.

Reads, Segment index writes, Log behavior, and gRPC are outside the scope of this Store-level benchmark.

The benchmark flushes and closes the file after the timed append loop. This flushes Go's userspace buffer to the operating system but does not, by itself, establish `fsync`-level durability.

## 6. Buffer configurations
The pilot used:
- `0` — existing/default `bufio.Writer` behavior;
- `4096` bytes;
- `16384` bytes;
- `65536` bytes;
- `262144` bytes.

These are pilot configurations, not yet the locked final configuration set.

## 8. Correctness checks
The current benchmark checks:
- Store's tracked size against the expected total framed bytes;
- final file size against the expected total framed bytes;
- successful flush and close.

These checks do **not** yet verify that every record can be read back and matches the expected payload. Add read-back verification to a correctness test or benchmark validation path before final results are accepted.

A result is invalid if the benchmark errors, expected sizes disagree, or the required read-back check fails.

## 11. Threats to validity
Potential threats include operating-system scheduling, background processes, CPU frequency and thermal variation, filesystem and storage-device effects, OS page cache, benchmark overhead, insufficient repetitions, and the interaction between buffer size and record size.

The current benchmark's reported `ns/op` is an average over operations in a run, not a latency distribution. Per-operation latency sampling has overhead and should be implemented and assessed separately if percentile latency is required.

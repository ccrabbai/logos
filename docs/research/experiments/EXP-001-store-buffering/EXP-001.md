# EXP-001 — Effect of Store Buffer Size on Append Performance

## Status

Planned

## 1. Research Question

How does the Store buffer size affect append throughput and latency in Logos under a controlled append-only workload?

## 2. Motivation

Logos uses an in-memory `bufio.Writer` between the Store append path and the underlying filesystem. The current implementation therefore contains a buffering policy that may affect the frequency and size of filesystem writes.

This experiment isolates buffer size as a controllable variable and measures its effect on append performance.

This experiment is intended to characterize the behavior of the Logos storage implementation. It does not, by itself, establish that one buffering policy is universally optimal or that Logos outperforms another storage system.

## 3. Experimental Variable

### Independent Variable

`StoreBufferBytes`

| Value | Meaning                                  |
| ----: | ---------------------------------------- |
|   `0` | Existing/default `bufio.Writer` behavior |
| `> 0` | Explicit `bufio.Writer` buffer size      |

The baseline configuration must preserve the existing Logos behavior.

## 4. Measurements

The experiment will measure:

* append throughput
* median append latency
* p95 append latency
* p99 append latency

Where appropriate, raw observations will also be retained so that the reported statistics can be independently recomputed.

## 6. Workload

Initial workload:

* append-only
* fixed record size
* fixed record contents/generation procedure
* fixed number of records
* fixed concurrency

Reads are excluded from the initial experiment because `Store.Read` and `Store.ReadAt` explicitly flush the Store buffer before reading. Including reads would therefore introduce another buffering interaction.

## 7. Buffer Configurations

To be finalized before the measurement phase.

The baseline configuration will use:

`StoreBufferBytes = 0`

Additional configurations will use explicit buffer sizes.

## 8. Correctness Requirements

Every benchmark run must verify that:

* the expected number of records was appended;
* the Store remains structurally valid;
* records can be read back;
* no unexpected append errors occurred;
* the benchmark did not silently lose records.

A performance result from a failed or invalid run must not be included in the final comparison.

1. Build Logos from a recorded Git revision.
2. Record the experimental environment.
3. Prepare the storage location.
4. Apply the selected buffer configuration.
5. Execute the benchmark.
6. Verify correctness.

## 18. Scope Boundary

This experiment does not establish:

* universal optimal buffer size;
* filesystem-independent performance;
* production performance under all workloads;
* durability guarantees;
* superiority over Kafka, databases, or other storage systems;
* a general law about storage systems.

It characterizes the behavior of the Logos Store under the specified experimental conditions.
